# 文档写法

这份规范管 `docs/api/` 下的文档怎么写。`docs/internals/` 是设计记录，不受它约束。

结构照 MDN：参考文档分**类页**和**成员页**两种，教人动手的内容写成**指南**。样板是 [`UIButton`](api/ui-button.md)、它的[成员页](api/ui-button/settitle.md)和指南[做一个按钮](guides/buttons.md)。拿不准时照它们写。

## 读者是谁

做过前端或图形开发、有扎实的通用开发概念，但**没碰过 iOS** 的人。

| 不用解释 | 必须解释 |
| --- | --- |
| 视图树、事件监听、回调、Promise、坐标变换、帧 | 安全区、Auto Layout 约束、layout guide、点（pt）、控件状态、SF Symbols 等一切 iOS 特有的东西 |

iOS 特有的词第一次出现时，用一句话直接说清它是什么。

## 四条原则

这四条管的是文档里所有介绍性、说明性的文字。它们比下面的模板和规则优先。

### 一、直接说它是什么，不用类比

不写「它相当于 X，有 N 点不同」「类似于 Web 的 Y」。类比要求读者先懂被类比的东西，再自己做减法；不懂 X 的读者完全看不懂，懂 X 的读者得到的也只是「它不是什么」。

直接陈述：它表示什么，管什么，由谁创建，什么时候存在。

| 不这样写 | 这样写 |
| --- | --- |
| `UIWindowScene` 大致相当于浏览器里的一个标签页，有四点不同 | `UIWindowScene` 表示 App 界面的一个实例。App 的每个窗口都属于某个场景 |
| `UIStackView` 相当于 `display: flex` 的容器 | `UIStackView` 把子视图沿一个方向排成一行或一列，并自动安排它们的位置和大小 |

写法参照 MDN 的接口页：第一句是「X 表示……」；用陈述句，成段地写；主语是对象和系统，不是「你」；不写「这一页分三部分」这类导览。指南和示例里教读者动手的部分可以用「你」。

页面末尾的对照表（与 iOS 原生写法的对照、与浏览器的对照）不属于类比：它不承担解释，只给已经熟悉另一套写法的人查对应关系。正文不依赖它也要能看懂。

### 二、站在读者的位置，提前回答他会想到的问题

每写一句话，先想读者读到这里会冒出什么疑问，然后就在这里回答，不往后放。

问题是从内容里长出来的，每个对象不一样，**没有通用的清单**：

- 读到「场景由系统创建」，读者会想：那什么时候才有？系统会不会把它收走？收走了我的界面怎么办？我手里还拿着它会怎样？
- 读到「颜色写成字符串」，读者会想：写错了 App 会崩吗？我怎么知道写错了？原来的颜色还在吗？
- 读到「点击对应的事件叫 `primaryActionTriggered`」，读者会想：按下去滑出去再松手算不算？禁用了还会收到吗？

动笔之前先把这些问题列出来。答不上来的问题不能跳过，也不能猜：去代码和验收用例里查；查不到的，按第四条处理。

### 三、告诉读者怎么做效果最好

只描述「会发生什么」不够。读者面对几种写法时，文档要给出推荐的做法，并说明为什么。

例子：场景被系统销毁后又来了新的场景，原来的窗口和页面要不要留着？文档要直接回答「不要留，在 `sceneconnect` 里按数据重建」，说明理由（留着会让系统收不回内存），再给出代码。

有不止一种合理做法时，先给推荐的，再说另一种适用于什么情况、代价是什么。

### 四、结论要有事实依据

- 每一条关于行为的说法，都要在代码、验收用例的断言或 `docs/internals/` 的实测记录里找得到出处。
- 找不到出处的，在该处标「**未在模拟器验证**」。
- **不替运行时说它没有的问题。** 「慢」「卡」「可能出错」这类结论必须有实测数据；没有数据就不写。运行时真有问题，记进问题清单交给运行时处理，文档不替它打圆场；运行时没有问题，文档就不该写有问题。
- 文档写到一半发现实现和应有的行为对不上，记下来，不要悄悄按实现写成「特性」。

## 三种页面

读者打开文档要的是两件事：**怎么用**和**查细节**。这两件事分开放：

| 页面 | 放在哪 | 回答什么 |
| --- | --- | --- |
| 类页 | `docs/api/<类>.md` | 这个类是什么、有哪些成员。一两屏读完 |
| 成员页 | `docs/api/<类>/<成员>.md` | 一个属性、方法或事件的全部细节 |
| 指南 | `docs/guides/<任务>.md` | 怎么用这些类做成一件事。按任务写，可以跨好几个类 |

参考文档（类页和成员页）只陈述事实，不教步骤。「为什么看不见」「推荐的做法」「常见用法」这类内容写进指南，类页的「参见」链过去。

## API 文档管什么，不管什么

API 文档只回答使用者的四个问题：

1. 这个东西能干什么。
2. 我怎么写。
3. 写完会得到什么。
4. 哪里会出错，出错时是什么样。

**API 文档不解释实现。** 桥怎么搭的、内存谁管、在哪个线程上调度、V8 和 ObjC 运行时内部怎么配合，这些都属于 `docs/internals/`。

一条内容能不能留在 API 文档里，只看一点：**它会不会改变使用者写代码的方式。**

| 内容 | 会改变写法吗 | 怎么处理 |
| --- | --- | --- |
| `blob()` 不复制数据，`text()` 会多占一份内存 | 会。下载大文件该选哪个取决于它 | 留下，写成结论：「下载大文件用 `blob()`，内存只占一份」 |
| 零拷贝靠 V8 的 `ArrayBuffer::NewBackingStore(...)` 接管 `NSData` | 不会 | 搬到 `internals/`，这里不提 |
| 文本解码在后台线程做 | 使用者关心的是结果 | 写成结论：「解码大文本时不会卡住界面」 |

具体规则：

- **写结论，不写机制。** 「这样更省内存」「这不会卡住界面」「这个值只能读一次」。不写为什么，也不链到 `internals/`：对外的文档站只发布 API 和指南，实现原理、项目说明、这份规范都不上站。
- **不出现运行时内部的名字。** V8、JIT、GC、run loop、delegate、原生层的类名和函数名都不出现。例外只有「对应的 iOS API」那一节。
- **不讲设计理由、实现思路和被否掉的方案。** 「为什么这么设计」「运行时内部怎么做的」属于 `internals/` 或 `project.md`，API 文档和指南里不出现，也不链过去。
- **对所有 API 都成立的背景，只在 [运行时怎么工作](api/how-it-works.md) 里讲一次。** 比如 JS 和界面在同一个线程上。各页需要时链过去，不重复解释。

## 类页

一个类一页。文件名是类名的短横线写法：`UIButton` → `ui-button.md`。一页讲了几个类的，拆开，每个类一页。

不是类的一组 API（`fetch()`、定时器、`application.storage`）照同样的结构写，「构造函数」「静态方法」换成「函数」。

顺序固定，没有的章节省略：

| 章节 | 写什么 |
| --- | --- |
| 介绍 | 第一句是「**X** 表示……」。再用一两段说它管什么、和谁配合。最后一行是**继承关系**：`EventTarget` → `NSObject` → … → 这个类，有页面的类写成链接。有指南的，指过去 |
| 构造函数 | 能 `new` 的写这一节：链到成员页，下面一句话说创建出什么。不能 `new` 的写一句「不能用 `new` 创建」并说明从哪里拿到实例 |
| 静态方法、静态属性 | 同上，一项一个链接加一句话 |
| 实例属性 | 一张表：属性（链到成员页，只读的在后面加 `<small>只读</small>`）、一句话说明。表前一句说还继承哪些类的属性，点名最常用的几个 |
| 实例方法 | 一张表：方法（链到成员页）、一句话说明。成员多时按用途分几张表，每张表前一句话 |
| 事件 | 一张表：事件名（链到事件页）、什么时候派发。继承来的常用事件也列，标明来自哪个类 |
| 概念 | 理解成员必需、又不属于某一个成员的东西，比如按钮的「状态」。一个概念一节。没有就省略 |
| 示例 | 一两个完整例子。第一个从空白 App 开始，复制进 `main.js` 能跑。每段后面有**效果** |
| 对应的 iOS API | ObjC 和 JS 的对照表 |
| 参见 | 指南和相关的类，每条说明为什么相关 |

类页上不写成员的细节。默认值、写错时怎样、报错原文，都在成员页上。

## 成员页

一个属性、方法或事件一页，放在类页同名的目录里。文件名是成员名全小写：`setTitle` → `ui-button/settitle.md`。构造函数是 `constructor.md`，事件是 `<事件名>-event.md`。

标题固定：

| 成员 | 标题写法 |
| --- | --- |
| 属性 | `` # `UIButton`：`role` 属性 `` |
| 方法 | `` # `UIButton`：`setTitle()` 方法 `` |
| 静态方法 | `` # `UIButton.buttonWithType()` 静态方法 `` |
| 构造函数 | `` # `UIButton()` 构造函数 `` |
| 事件 | `` # `UIControl`：`click` 事件 `` |

标题下面第一段是一句话：「**`setTitle()`** 方法……」。

然后按成员的种类，章节顺序固定：

| 属性 | 方法、构造函数 | 事件 |
| --- | --- | --- |
| 值 | 语法 | 语法 |
| 示例 | 参数 | 事件对象 |
| 对应的 iOS API | 返回值 | 什么时候派发 |
| 参见 | 异常 | 示例 |
| | 说明（可以省略） | 对应的 iOS API |
| | 示例 | 参见 |
| | 对应的 iOS API | |
| | 参见 | |

各章节写什么：

- **值**：类型；可读、可写（只读的写明「给它赋值抛 `TypeError`」）；默认值；每个取值的效果；会变的值怎么得知变了。可写的再加一个小节「写错时」，照抄报错原文，或者说明是警告。
- **语法**：一个不带语言标记的代码块，只写签名，比如 `setTitle(value, { forState })`。可选的参数用方括号。
- **参数**：每个参数一段，参数名单独一行加粗写成 `` **`value`** ``，下面一段说类型、取值、不传时怎样。options 对象的成员写成 `` **`options.forState`** ``。
- **返回值**：类型和含义。没有返回值写「无（`undefined`）」。返回 Promise 的写清兑现成什么、什么时候拒绝。
- **异常**：异常类型单独一行加粗，下面列出每种触发情况和报错原文。不抛的写「无」。
- **事件对象**：事件对象的类型，以及除 `type`、`target` 以外带的字段。能不能取消。
- **示例**：一两段代码，每段后面有**效果**或**结果**。可以沿用一个在代码里新建的变量，不依赖别的页面里的变量。
- **对应的 iOS API**：一行写出对应的 ObjC 成员，写法有差别的说清差在哪。

## 指南

一篇讲一件事，标题是要做的事：「做一个按钮」「做一个列表」「从网络取数据」。

| 章节 | 写什么 |
| --- | --- |
| 开头 | 一段话说这篇做成什么，链到涉及的类页 |
| 推荐的做法 | 有几种写法时先给结论 |
| 第一个例子 | 从空白 App 开始的完整代码和效果 |
| 一件事一节 | 读者会遇到的问题和想做的事，每节代码加效果 |
| 参见 | 涉及的类页 |

后面各节沿用第一个例子里的变量时，第一个例子之后紧跟一段代码，声明这些变量，并写一句「单独试某一节时，先写这几行」。第一个例子的变量建在 `sceneconnect` 的回调里，后面各节看不见它们；有了这一段，每一节复制出来都能单独运行，类型检查也能把整篇连起来查。

类页原来的「为什么看不见」「推荐的做法」「常见用法」都搬到这里。一个类内容不多时，可以几个类合写一篇。

## 规则

### 例子

1. **每段代码后面都有「效果」。** 写屏幕上看到什么、用户操作时发生什么、控制台输出什么。一条一行。
2. **完整例子从空白 App 开始。** 包括建窗口和页面的那几行，复制进 `main.js` 就能跑。
3. **除了类页的第一个例子，别的例子可以省略建窗口**，但不出现没交代过的变量：指南里在章节开头说明沿用了哪些变量；成员页的例子在代码里自己新建。
4. **小节标题是读者想做的事**：「禁用按钮」「加图标」，不是属性名。
5. **例子里用到的每个 API，本页或链接页里必须有说明。**

### 成员页

6. **每个属性写明：类型、可读、可写、默认值、含义。** 可读和可写各占一列，写「是」或「否」，不合并成「读写」。
7. **数值必须写单位。** 长度写「pt」并链到[单位](api/units.md)。没有单位的写明它是什么：比例、个数、优先级。
8. **枚举的每个取值都写效果**，不只列名字。
9. **布尔属性两种取值的效果都写。**
10. **会变的值写清怎么得知它变了**：派发哪个事件。没有通知的写原因。
11. **方法写明：参数、返回值、出错情况。** 报错信息照运行时抛出的原文抄。
12. **每个成员一页，不合并。** 写法相同的几个成员，各自的页面结构相同，各自写全；在类页上可以放进同一张表。

### 语言

13. **用直白的技术词。** 不用「钉」「塌」「吃掉」「兜底」这类口语和比喻。
14. **一个概念只用一个词**，全站统一。
15. **一句话只说一件事。** 主语明确，短句。
16. **只写现在。** 不讲「原来怎样、后来改了」，那些进 `internals/`。
17. **正文中文。** 标识符、取值、报错信息保持英文原文。

### 事实

18. **类型和可读可写以 `types/` 为准。** 文档和类型定义不一致时，先查清哪边对。
19. **没在模拟器验证过的效果，标「未验证」。** 默认不标的都是验证过的，或直接来自代码。
20. **不知道的不写。** 不凭印象填数字。
20a. **只写有什么。** 不列运行时没有的东西，也不写某个类还缺哪些能力、以后会不会有。读者知道这是一个全新的 JS 运行时，查不到的成员就是没有。还没做的能力是我们自己的待办，记在 `internals/api-gaps.md` 和 `project.md` 第 7 节。

### 提示块

21. 只用一种提示块，写成 `> **注意**：…`。用于不看就会出错的地方。一页里不超过五六处，多了就没人看。

## 英文版

对外的文档站默认英文，中文在 `/zh/` 下（2026-11-19 定）。中文是原文：`docs/api/X.md` 的英文版是 `docs/en/api/X.md`，指南同理。

- **改一页，两种语言一起改。** 新增、修改、删除一个中文页面，同一个改动里改它的英文版。只改一边等于两边说法不一样。
- **结构和中文一模一样**：frontmatter 一字不差；`#` 到 `####` 的标题个数、级别、顺序一样；代码块个数一样。这样两边才对得上，锚点也能按位置换算。
- **代码照抄**，只翻译注释和中文字符串，翻了字符串就同步改「效果」里写的输出。代码本身在演示中文的（按中文地区格式化、UTF-8 字节数这类）原样保留。
- **语气照 MDN 英文版**：陈述句，美式英语，标题句首大写。固定的译法：参见 See also、示例 Examples、对应的 iOS API Corresponding iOS API、值 Value、语法 Syntax、参数 Parameters、返回值 Return value、异常 Exceptions、写错时 Invalid values、未在模拟器验证 not verified in the simulator。成员页标题写成 `` `UIButton`: `setTitle()` method ``。
- **核对**：`python3 docs/check-translation.py docs` 检查每个中文页面都有英文版、结构一致、英文正文里没有中文。
