# AI 协作规则

上面引入的 `docs/project.md` 是项目说明（项目定义、技术选型、目录约定、SOP、进度）。本文件只记录 AI 在这个项目中必须遵守的规则。

## 沟通

- 全程使用中文，包括中途的进度说明和最终回复。
- 回复简洁，先说结论；不复述用户的话。

## 严格执行 SOP

- 按 `docs/project.md` 第 5 节的流程：讨论 → 明确 → 用户确认 → 实现 → 检查 → 验证 → 提交 → 记录。
- **没有用户明确确认，不写代码、不写入仓库。** 讨论阶段只给方案和取舍。
- 用户只回答了部分问题时，未回答的部分按推荐方案处理，并在回复中说明。
- 实现中发现需要改变已确认的方案，立即停下，回到讨论。
- 遵守原生层边界：原生层只能新增启动壳、运行时、能力暴露代码，不能新增任何调度代码。

## 能力边界

AI 可能在两种环境中工作，规则不同：

| 环境 | 能做什么 | 规则 |
| --- | --- | --- |
| **Claude Code**（本地，可以执行命令） | 读写文件、执行命令 | 构建和运行类命令（`xcodegen`、`xcodebuild`、`scripts/*.sh`）可以直接执行；**会改变仓库状态或系统环境的命令**（git commit / push、删除、移动、安装软件）执行前先征得用户同意 |
| **云端对话**（Cowork，只能写文件） | 只能往仓库写文件 | 不能执行命令；需要操作时给出完整的、可以直接复制执行的命令，由用户执行 |

- 每一步完成后给出 commit 命令，格式为 `<范围>: <中文描述>`。在 Claude Code 中经用户同意后可以直接提交。

## 写入文件

- **写入前先读取**仓库中的现有文件，确认用户没有修改过，不覆盖用户的改动。
- **生成文件和写入仓库不能同时执行**（云端对话）：等文件完整生成后再写入仓库。
- **写入后检查**：核对仓库中文件的大小或内容，确认写入的是新版本。
- 不能写入的位置（被系统拦截）要告诉用户，并把内容交给用户自己创建。

## 质量

- 没有实际运行过的代码和结论，明确标注"未验证"。
- 能在本地检查的先检查，比如 C++ 对照 V8 头文件做语法检查、脚本做语法检查。
- 不确定的事实先查证，不凭记忆下结论。
- 不做没被要求的事。发现相关问题时，先说明，再询问是否处理。
- 出错时直接承认，说明原因和修复方式。

## 文档

- **写或改 `docs/api/` 下的文档前，先读 `docs/writing-guide.md`**，按它写。样板是 `docs/api/ui-button.md`。
- 读者是做过前端或图形开发、但没碰过 iOS 的人。页面顺序固定：完整例子 → 常见用法 → 概念 → 成员说明 → 对照表 → 还不能做的。
- 每段示例代码后面写「效果」；每个数值写单位；可读和可写分开写。
- 没在模拟器验证过的效果标「未在模拟器验证」，不凭印象写。
- 示例代码要能通过严格模式的类型检查：可空的值先判空，代码块是完整语句。
- 还是旧写法的文档，**碰到哪篇就把哪篇整篇改成新写法**，不要在旧写法的文档里继续追加旧写法的内容。
- `docs/internals/` 是设计记录，不受这份规范约束。
