# 验收怎么判通过

验收套件（`acceptance/`）跑在模拟器和真机上，结果是 App 打出来的日志。这一页记的是「一遍验收算不算通过」由谁判、怎么判。

2026-11-16 之前是人判的：`run-sim.sh` 只负责启动和显示日志，没有退出码；跑完没跑完靠「很久没有新的 ✓」猜；通过多少条靠 `grep` 数。一份外部审查指出了这一点，连同断言函数本身的一个问题（见下面[断言比的是严格相等](#断言比的是严格相等)）。

## 一条命令，一个退出码

```bash
cd acceptance && npm run verify                 # Debug
```

```bash
cd acceptance && npm run verify -- --release    # Release
```

`scripts/verify.mjs` 调 `ios/scripts/run-sim.sh`（真机是 `run-device.sh`，见[真机](#真机)），把输出存到 `acceptance/build/verify-<配置>.log`，等 App 打出结束标记，然后判结果。结果另存一份 JSON（`verify-<配置>.json`）。退出码 0 是通过，1 是没通过，2 是命令行写错了。

没通过有五种情况，原因打在输出的最后：

| 情况 | 怎么知道的 |
| --- | --- |
| 编译或者安装失败 | `run-sim.sh` 退出了，而运行时的第一行输出还没出现过 |
| 有断言失败 | 日志里有 ✗ 的行。步骤中途抛了也是一条 ✗ |
| 没等到结束标记 | 过了期限（默认 25 分钟，`--timeout=<分钟>` 改） |
| App 提前退出 | `run-sim.sh` 退出了，App 起来过，但没有结束标记。崩溃和被杀都是这种 |
| 断言名单和基线对不上 | 见[基线](#基线每一遍该出现哪些断言) |

分成两个文件：`verify.mjs` 只管启动、存日志、等；怎么判在 `lib/report.mjs`，全是纯函数，用存好的日志片段测（`npm test`，不启动模拟器）。

## 结束标记

所有步骤跑完之后，App 打一行：

```
[acceptance] done {"asserts":3700,"failed":0}
```

runner 等的就是它。等到了才数结果；期限内没等到算失败。

「跑完」在 App 里分两层判（`src/main.js` 的 `finish`）：

1. 排队的步骤一个接一个跑完；网页那一步、所有权那几组、三张和网页的比对，都把「做完了」作为 Promise 交了出来，等它们。
2. 最早那批步骤（三十多步）的异步部分没有交出 Promise，各等各的。所以再加一条：**连续 5 秒没有新的断言**。它们的期限最长 10 秒，而排队的步骤要跑几分钟，到这里早就过了。

第 2 条是近似，不是保证。把最早那批步骤改成一步一步顺序跑、每步交出 Promise，才能去掉它；那是三十多个文件的改动，这一步没有做。

标记里的两个数是共用的断言函数自己数的，只是给人看的。**runner 不用它们判结果**，它数的是日志里的行，原因见下一节。

## 数的是日志里的行

一遍验收的日志里有四千多行 ✓，其中约三千七百行是共用的 `assert()` 打的，其余四百多行是各个步骤自己用 `console.log` 打的：有的是自己写的比较（`ok ? '✓' : '✗'`），有的是真实触摸之后打的一行，有的只是说明屏幕上该看到什么。

runner 数的是行，不分来源：前缀之后只有空白、然后是 ✓ 或 ✗ 的行算一条断言，`!` 开头的算一处未验证。这样历史上的数字接得上，自己打 ✗ 的那些也照样能让这一遍不通过。

没解决的：那四百多行里无条件打 ✓ 的，证明不了任何东西，却算在通过数里。要解决得逐个步骤改成走 `assert()`。

## 断言比的是严格相等

`assert(label, actual, expected)` 原来比的是 `String(actual) === String(expected)`，于是：

| 写法 | 原来 | 现在 |
| --- | --- | --- |
| `assert(label, 1, '1')` | 通过 | 失败 |
| `assert(label, { a: 1 }, { a: 2 })` | 通过（两边都是 `[object Object]`） | 失败 |

现在比的是 `===`，外加两条：`NaN` 和 `NaN` 算相等；0 和 -0 算相等（所以没有用 `Object.is`）。两边写出来一样却没通过时，失败的那一行会说明原因（类型不同，或者不是同一个对象），不然只看到「得到 1，期望 1」。

要比内容的，在调用的地方写清楚比什么：数组用 `join(',')`，对象挑字段，故意按字符串比的写 `String(x)`。

改的时候量过：3200 个调用点里受影响的只有 5 处，都在网页那一步，是从网页标题里切出来的字符串和数比。改成先 `Number()` 再比。

## 基线：每一遍该出现哪些断言

**2026-11-21 起不再维护。** 验收改成只在真机上跑，而真机上出现的断言和模拟器不一样（见[真机](#真机)），基线只能在模拟器上记；为了它每一批再在模拟器上补跑一遍，和「只用真机」相违，这一遍本身还时常被访问外网的断言拖住。所以停了：`acceptance/baseline/simulator.txt` 停在 2026-11-21 之前的那一版，新加的断言不再进去。代价是「某组检查这一遍悄悄没跑」不再被自动拦住，只能靠结果里的未验证列表和人看。下面记的是它当时的做法，偶尔要在模拟器上跑时带 `--no-baseline`。

只数失败数有一个漏洞：**少跑的断言是看不见的。** 一个步骤中途抛了，它后面的断言都没跑，失败数只多一条。弹窗那一步出过一次这种事。

所以另有一份名单 `acceptance/baseline/simulator.txt`，提交在仓库里，列出每一遍该出现的断言的名字。一行一条，开头两个字符是记号：

```
# 注释
+ alpha 默认 #
? 对照组在下载结束之前被回收
```

| 记号 | 含义 |
| --- | --- |
| `+ ` | 每一遍都必须出现，少了算失败 |
| `? ` | 可以缺。那几组对时序敏感的检查有时自己报未验证，它们的断言那一遍就不出现 |
| `# ` | 注释 |

几条定法：

- **名字**是 ✓ 或 ✗ 之后到第一个「 = 」为止的那一段，里面的数字统一换成 `#`。断言的名字里常带量出来的数（耗时、字节数），不换的话每一遍都不一样。
- **比的是名字的集合**，不比每个名字出现几次。
- **每行都带记号**，没有「不带记号就是必须出现」这种写法。数字换成 `#` 之后有的名字自己以 `# ` 开头（`# MB 的 Blob：长度`），会和注释分不清。
- **这一遍出现、基线里没有的名字也算失败。** 新加了断言就要更新基线，这样基线的每一次变化都在提交里看得见。
- **没跑完的那一遍不报基线的差异。** 那时名单必然缺一大片，是后果不是原因。

更新基线：

```bash
cd acceptance && npm run verify -- --update-baseline
```

这一遍全部通过才会写。新名字进「必须出现」；原来必须、这一遍没出现的被去掉（那条断言被删了）；已经是「可以缺」的一直留着。

某组检查这一遍报了未验证、它的断言因此没出现时，加上 `--mark-missing-optional`：没出现的不去掉，改记成「可以缺」。

更新基线时，被去掉的名字会逐条列出来。这是后来加的：有一次用一遍「有三组检查报了未验证」的结果更新基线，那三组的十来条断言被当成删掉的悄悄去掉了，下一遍它们照常出现，反而被报成「基线里没有」。

「可以缺」现在有 6 条，都是实际观察到的，来自三组检查：

| 哪一组 | 它什么时候报未验证 | 断言 |
| --- | --- | --- |
| 下载期间的 GC | 对照组没在下载结束之前被回收（GC 没赶上） | 2 条 |
| 动画事件 | 8 秒内没等到动画的开始和结束事件 | 3 条 |
| 大文件写入期间定时器照常跑 | 写入的兑现排在了 0 毫秒定时器的前面，顺序控制不了 | 1 条 |

做这一步的当天跑了六遍完整的验收，GC 那一组碰上两次，动画那一组碰上一次。记成「可以缺」之后，碰上的那一遍照样通过，未验证的那一处列在结果里。

这是个折中。对「可以缺」的名字，runner 分不清「那组检查这一遍没轮到」和「那条断言被删了」。要分清，得让每一处未验证说明它没验的是哪几条，见[这一步没有做的](#这一步没有做的)。

基线是在 iPhone Air 模拟器上记的。换了设备或者系统版本，名单会有出入（有的断言只在某个系统上跑），用 `--no-baseline` 只看断言不比名单。真机上（`--device`）不比基线；2026-11-21 起基线也不再维护（见上）。

## 真机

2026-11-21 起验收直接跑在真机上：

```bash
cd acceptance && npm run verify -- --device
```

`--device` 让 `verify.mjs` 调 `ios/scripts/run-device.sh`，其余照旧：存日志、等结束标记、判结果。日志和结果的文件名前面多一个 `device-`。

`run-device.sh` 前面几步和 `run-sim.sh` 一样（生成 `ios/`、打包 JS），后面是：

1. **挑设备**：第一台用线连着的 iPhone（`devicectl list devices`），`NACRE_DEVICE` 可以指定。放在编译之前，没连手机不白编几分钟
2. **编译时不签名**（`CODE_SIGNING_ALLOWED=NO`）：工程里不写团队和描述文件，换一台 Mac 也能跑
3. **拷一份出来自己签**（`ios/scripts/device.mjs sign`）：改包名、嵌描述文件、写 entitlements、先签里面的 framework 再签 App。拷出来签，是为了让编译产物保持没签名，下次增量编译不受影响
4. `devicectl device install app`，再用 `devicectl device process launch --console --terminate-existing` 启动。`--console` 把 App 的 stdout 接到终端，和模拟器的 `--console-pty` 一样，所以 runner 认的那几行（`[JS]` 开头、结束标记）不用改

**包名是 `com.test.test`**，不带任何组织或项目的标识（`NACRE_DEVICE_BUNDLE_ID` 可以换）。只改 App 的 `CFBundleIdentifier`，里面的 framework 不动。

**签名不用在 Apple 的网站上登记包名。** `device.mjs` 在本机找一份描述文件：包含这台设备、没过期、`application-identifier` 是 `<团队>.*`（通配）或者正好是 `<团队>.<包名>`；再找一个装在钥匙串里、在这份描述文件证书名单上的签名身份。Xcode 自动管理签名时生成的那份通配描述文件就满足。两份都能用时，正好是这个包名的优先：推送这类能力只有显式包名的描述文件签得进去（2026-11-21 做推送时加的）。要用它就把包名和描述文件交给环境变量 `NACRE_DEVICE_BUNDLE_ID`、`NACRE_PROFILE`，仓库里不写任何账号相关的东西。entitlements 从描述文件里那份出发，把通配的 `application-identifier` 和 `keychain-access-groups` 换成具体的包名。通配的描述文件签不了要显式包名的能力（推送、关联域名），验收用不到。

描述文件里的日期和证书是 plist 的 `<date>`、`<data>`，`plutil` 整份转不成 JSON，所以按字段取（`plutil -extract <键> raw`：日期给 ISO 字符串，二进制给 base64，数组给元素个数）。证书的 SHA-1 和 `security find-identity` 列出的对上，就是那个身份。

**真机上不比基线**，只看有没有失败、有没有中途抛错。真机上有一批检查走另一条分支：剪贴板不自动读写（免得冲掉手机上的内容）、相机这种来源可用、权限还没问过的不自动弹框，所以出现的断言和模拟器不一样。

**本机的测试服务真机上连不到**：App 里的 `127.0.0.1` 是手机自己。流式响应那一步照旧报未验证、整步跳过。

**这个包名第一次装到国行 iPhone 上**，第一次联网时系统会问要不要允许它使用无线数据。没点允许之前，App 的网络请求一律报「The Internet connection appears to be offline」，验收里访问外网的那几组会失败。点一次就记住了，以后不再问。

**也有不弹框、却一直断网的时候。** 2026-11-21 做推送那天，Debug 的包连着几遍联不上网（系统报 `type = none`），手机上没有弹框，同一时间的 Release 是好的；把手机上的 App 全删掉重装，第一次启动弹了框，点允许之后就好了。为什么那几次不弹没查清。遇到「这一遍所有联网的断言都失败、网络状态是 none」先这样处理：删掉 App 重装，盯着手机点允许。

## 只跑指定的步骤

改一个步骤不用等完整的一遍：

```bash
cd acceptance && npm run verify -- --steps=coreLocation,localAuthentication
```

名字是 `src/main.js` 里的步骤名，带不带 `step` 前缀都行。

几条定法：

- **过滤是打包时写进产物的。** App 里没有读启动参数的接口，为这个加一个不值。runner 通过 `NACRE_ESBUILD_ARGS` 这个环境变量把 `--define:globalThis.__NACRE_STEPS__="…"` 交给打包器，入口文件里读 `globalThis.__NACRE_STEPS__` 的那个写法被整个换成一个字符串；平时没有这个参数，读到的是 `undefined`，全部都跑。
- **建窗口那一步总是跑**：别的步骤要它建的页面和区块。入口顶层引入的那六段（`console`、`application`、错误出口等）也照常跑，它们是引入时就执行的。
- **只选了排队的步骤时，不等开头那 10 秒。** 那 10 秒是留给最早那批步骤的异步部分的。
- **不比对基线**，只看有没有失败。结果里写明只跑了哪几步，通过时说的是「这几步通过（不是完整的一遍）」。`--steps` 和 `--update-baseline` 不能一起用。日志和结果另存成 `verify-<配置>-steps.*`，不盖掉完整那一遍的。
- **过滤有没有生效要核对。** App 在结束标记里报它按哪几步过滤的。要求只跑几步而 App 跑了全部，或者反过来，或者两边的步骤不一样，都判不通过。不核对的话，一次没生效的过滤会让人把完整的一遍当成那几步的结果。
- **步骤名写错当场拒绝**，并列出有哪些步骤。runner 的步骤表是用正则从 `src/main.js` 里认出来的，认不出任何步骤时会报「认法过时了」，不会安静地给一张空表。App 里还有一道底线：过滤里有它不认识的名字，记一条失败。

### 步骤之间的依赖：量出来的

把五十七个步骤各单独跑了一遍。五十五个单独跑就通过，两个离不开导航那一步：

| 步骤 | 单独跑时 | 原因 |
| --- | --- | --- |
| 模态 | 1 条断言失败 | 它有一条断言认定页面在导航控制器里 |
| 所有权 | 1 处自己报未验证 | 它要用导航那一步留下的导航控制器 |

这两处登记在入口文件的 `STEP_NEEDS` 里：选了左边的，导航那一步跟着跑。登记之后两步单独跑都通过。

别的步骤单独跑时报的未验证，和它们在完整的一遍里报的是同一些（要真实触摸的、要点系统界面的），不是因为缺了别的步骤。

## 排队的步骤是 async 的，抛了也要报

排队的步骤（`later`）返回 Promise 时，入口等它结束再跑下一步。原来写的是 `then(next, next)`：Promise 被拒绝（`async` 的步骤中途抛了）也直接跑下一步，**不报任何失败**，那一步后面的断言没跑也看不出来。2026-11-20 接页面的方向和状态栏时，第一次红跑因此显示「全过」才发现。现在被拒绝时照同步步骤的写法记一条 ✗。键盘、网页那两步也是 `async` 的，以前出错同样会被这样掩盖。

## 机器忙的时候结果不可信

验收里有一批断言对时序敏感：取消请求留的窗口是 5 秒，每帧回调要在几秒内走够帧数，输入框的焦点要在 6 秒内交出去。机器被别的编译占着时，这些窗口不够用。

做「只跑指定步骤」的那天晚上，有五个对话同时在各自的分支上编译，量到的是这样：

| 那一遍 | 机器负载 | 主线程最长被卡 | 结果 |
| --- | --- | --- | --- |
| Debug | 18 | 没记 | 4 条失败，另有二十多条没出现 |
| Debug | 12 以上 | 5.8 秒 | 4 条失败，16 条没出现 |
| Debug | 6 到 10 | 2.1 秒 | 1 条失败，1 条没出现 |
| Release | 12 左右 | 3.6 秒 | 通过 |
| Debug（编译都停了之后） | 3 到 6 | 2.1 秒 | 通过 |

取消请求那一条失败的经过：定时器定在 200 毫秒后取消，服务端 5 秒后才回；主线程连着被卡了 5.8 秒，定时器还没轮到，响应先回来了。

所以**验收要在没有别的编译在跑的时候做**。几个对话并行时，它们只编译、不跑模拟器，验收排在它们都停下之后。门禁本身没有做错：那几遍它都判了不通过，没有把不可信的结果放过去。

### 日志要原样存字节

同一个晚上还查到 runner 自己的一个问题。它原来把 App 的输出一块一块转成字符串再存进日志，有一块正好断在一个汉字的中间，前后两半各自变成乱码，三条断言的名字因此和基线对不上，被报成「少了三条、多了三条」。现在存的是原样的字节；逐行看的那一份用 `StringDecoder`，它会把半个字留到下一块。

### 行尾的回车要全部去掉

日志的每一行以回车加换行结尾，偶尔是两个回车。runner 原来只去掉一个，剩下的那个让整行对不上断言行的格式，这一行就被跳过了，不报任何东西。2026-11-17 查到：Release 的一遍里有一条 `Intl` 的比对落在这样的行上，被报成「基线里有、这一遍没出现」，而日志里明明有它。

报成「没出现」还算是看得见的。同样的事落在一条 `✗` 上，这条失败就不会被数到。现在行尾的回车全部去掉，有一条用例盯着。

### 几条断言自己的问题

验收跑多了之后，查出来过几条断言本身的毛病，和运行时无关：

- **网页那一步要等它跑完，后面的步骤才能盖住它。** 它的异步部分会一直跑到后面的步骤中间，而「页面出现和消失」那一步会呈现全屏的模态页把网页盖住，被盖住的网页不再更新，网页那一步的断言就时过时不过（Release 连着两遍各挂一条，不是同一条）。改成那一步等网页跑完。更早的时候把同一条断言的失败归因于面板加高，那个归因多半不对。
- **「解析不了的地址报加载失败」原来只等 2.5 秒。** 那时一次外网请求要 1 到 2.5 秒，六遍里挂过三遍。等待放到了 10 秒。
- **对着 httpbin 比并发耗时的那一条会被限流。** 它发 10 个并发请求，那个站会回 429，模拟器和真机上都偶发过。
- **钥匙串和文件读写里「写入期间定时器照常跑」只单边有效。** 定时器先跑到能证明重活在后台，没跑到什么都证明不了，所以没跑到时报未验证，不算失败。
- **网页开着时 App 写的 cookie，写完立刻读。** 那条 cookie 要先过一趟网页的进程，真机上三次挂两次，模拟器的 Debug 也挂过。2026-11-20 改成最多等 3 秒、每 100 毫秒读一次。
- **WebSocket 的「close 之后是 CLOSING」赌连接还没失败。** 连的是真的外网服务，连接有时在 `close()` 之前就自己失败了，那时是 `CLOSED`。照 WHATWG，对 `CLOSED` 的连接调 `close()` 什么都不做，所以 2026-11-20 改成按调用前的状态算期望值：之前是 `CLOSED` 就还是 `CLOSED`，否则是 `CLOSING`。

## 故障注入：每一种没通过都试过

门禁自己也要验：一个永远返回 0 的 runner，平时看不出来。下面每一种都实际做了一遍，看退出码和点名的原因（iPhone Air 模拟器，iOS 27.2）。

| 注入了什么 | 退出码 | runner 给的原因 |
| --- | --- | --- |
| 什么都不注入 | 0 | 通过 |
| 指定一个不存在的模拟器 | 1 | 编译或者安装失败，App 没有启动 |
| 期限只给 36 秒 | 1 | 期限内没等到结束标记（这时已经跑了 1887 条） |
| 跑到一半用 `simctl terminate` 把 App 杀掉 | 1 | App 没打结束标记就提前退出了（这时已经跑了 2275 条） |
| 字符串和数相比（改严格相等之前就有的 5 处） | 1 | 5 条断言失败，每条写着「写出来一样，类型不同」 |
| 一个步骤开头就抛异常 | 1 | 1 条失败点名是哪一步；基线里少的二十来条正是那一步的断言 |
| 比较两个内容不同的对象 | 1 | 1 条失败，写着「写出来一样，但不是同一个对象」 |
| 删掉一条断言 | 1 | 基线里有、这一遍没出现，点名那一条 |

## 定了不做的两条

（2026-11-18 定。来自 2026-11-17 那份外部审查。）

**不按改动自动挑验收步骤。** 手动挑已经有了（`--steps`）。自动挑要一张「哪个文件对应哪几步」的表，那是又一份手写的来源；而且它替代不了完整的一遍：只跑几步不比对基线，原生的共享文件（桥、参数转换、事件）一改，每一步都可能受影响，挑不出来。

**Debug 和 Release 不同时跑。** 同一台模拟器上跑不了：两个配置是同一个包名，装不下两份；换成两个包名的话权限按包名记，各要授一遍；同一时刻也只有一个 App 在前台。再建一台模拟器的话，基线是在 iPhone Air 上记的，而且两遍同时跑正是上一节说的那种负载，时序敏感的断言会挂。两遍接着跑就行。

## 这一步没有做的

- **外网的请求换成本机的服务。** 验收里有十几处访问 `httpbin.org`，网络不好时会挂，和代码无关。本机的测试服务已经有了（`scripts/test-server.mjs`，流式响应那一步在用，runner 跑验收时自己起、跑完自己停；端口被占着时认为已经有一个在跑，直接用），但原来那些访问外网的断言还没有换过来。
- **81 处「未验证」没有改。** 它们还是自由格式的日志，runner 按 `!` 开头的行数出来列在结果里。理想的做法是每一处说清楚它没验的是哪几条断言，这样「可以缺」就不用靠观察来记。
- **没有接进 CI。** CI 的机器上没有模拟器环境和 V8。
- **真机上不比基线，基线也不再维护。** 见[基线](#基线每一遍该出现哪些断言)。

## 验收套件为什么按真的 JS 工程来搭

`acceptance/` 是验收套件的 JS 源码（2026-11-13 之前叫 `app/`）。它和 `ios/` 平级，**不在 `ios/` 里面**——第 4 节的 Android 计划是「同一份业务 JS，按平台分支调用各自的原生能力」，而 `ios/` 的约定是「永远表示运行时源码」，跨平台的 JS 放进去从一开始就错了。

**它按真的 JS 工程结构来，这是有意的。** 这个客户是 JS 开发者，如果我们自己的第一个客户都不走 `package.json` + 依赖 + 打包那一套，「社区工具链能不能对准 Nacre」这件事就验不到。

| | |
| --- | --- |
| 打包 | esbuild，`npm run build` → `acceptance/ios/JS/main.js`。**不用 vite**（dev server、HMR、index.html 对我们全没用），也不用 webpack（经典输出给每个模块包一层 CommonJS 壳，而 esbuild 的 scope hoisting 产物几乎就是源码顺序拼起来——运行时没有 source map，产物越接近源码越好） |
| 硬约束 | `--format=iife`（运行时编译 classic script，ESM 的 `import` 直接抛）、`--platform=neutral`（不能注入 `process` / `Buffer` 的 polyfill）、不压缩 + `--charset=utf8`（报错行号只能靠人去产物里对） |
| 类型 | 像真客户一样把 `@nacrejs/types` 装成依赖（`file:../packages/types`），靠 `src/main.js` 里的 `/// <reference types="@nacrejs/types" />` 引进来，**不走相对路径 include** |
| 版本 | esbuild 和 typescript 都钉死在 `package.json`，lock 文件提交 |

## 这件事当场抓到两个问题

**1. `packages/types/package.json` 的 `files` 白名单漏了 `ios/`。** 拆分 `ios.d.ts` 的时候没跟着改，`npm pack --dry-run` 只有 5 个文件——这个包一旦发布，装的人拿到的 `ios.d.ts` 是一串指向空气的 `/// <reference path>`，**一个 iOS 类型都没有**。而 `check-api.sh` 和 `tsc` 都查不出来，因为它们走的是相对路径 include，压根没问过「这个包发出去是什么样」。

修法是**把 `files` 删掉**：这个包里除了 `.d.ts` 和 README 什么都没有，白名单只会再漂一次。

**2. 类型检查一直跑在没钉版本的 TypeScript 上。** `npx -y -p typescript tsc` 拉的是**最新**，实测当时已经是 **7.0.2**（Go 重写版），而且是无声变过去的。现在钉成 5.9.3。

## 一条测不出东西的验收

原本想用「把 `packages/types/package.json` 的 `types` 字段改错，类型检查要报错」来验包的入口。**这条是无效的**——Node/TS 解析在 `types` 指不到时会回落到 `index.d.ts`，所以那个字段不承重，改错了照样过。

真能证明的测法是**把 `/// <reference types="@nacrejs/types" />` 那行去掉**：`UIView`、`UIWindow` 连 `console` 一起全部 `Cannot find name`。这才说明全局确实是通过这个 npm 依赖进来的。

## 怎么分文件

跨段共享的只有这几样：`assert`（在 `src/support.js`）、`vc` 和 `win`（由 `stepWindow` 建好后写回 ctx），以及版面给的 `section` / `column` / `dock`（见下一小节）。其余全是段内局部。

- 顶层那几段（console、application、错误出口、前后台、包装与场景）在脚本顶层执行，所以**作为副作用 import**，执行顺序就是 `src/main.js` 里的 import 顺序
- 场景回调里那几段是 `export function stepXxx(ctx)`

**CALayer 那段没有自己的文件**——它嵌在 Auto Layout 的块里，用的是同一张卡片。拆的时候 `tsc` 当场报了 `'}' expected`，同理 `timers` 用到 `win` 也是 `tsc` 报出来的。**跨段引用靠类型检查兜住，不靠肉眼。**

## 版面：一步一个区块，从上往下排

验收界面是一个纵向滚动的「瀑布」（`src/waterfall.js`）：每一步向它要一个区块——一行小标题加一块固定高度的内容区——区块按步骤的先后从上往下排，排不下就滚。输入框那张卡片例外，它要验的是贴着键盘走，所以留在根视图上，瀑布的底边接在它上面。

**以前不是这样**：各步把东西直接摆在根视图上，位置各写各的固定坐标（`new CGRect(230, 412, 150, 90)`、`bottom: -352`），十几块互相压着；坐标还是按 iPhone Air 的 420 pt 宽写的，换到 390 pt 的 iPhone 14 上最右一列被切掉。

搬的时候定的几条：

| | 做法 | 为什么 |
| --- | --- | --- |
| 内容区的宽度 | 横向铺满安全区，不替各步留边 | 各步本来就自己写「左右各留 16」。这样内容区在版面上的角色和以前的根视图一样，`card 宽 = 安全区宽 - 32` 这类断言**一个数都不用改** |
| 滚动视图放哪 | 整个待在安全区里面 | 里面每个区块的安全区就等于它自己的范围，各步拿 `host.safeAreaLayoutGuide` 当边界用，不会被刘海掺进来 |
| 区块什么时候建 | 进入这一步时同步建 | 区块的先后就是调用的先后。模态那一步的按钮是 600 ms 之后才加的，区块要提前建好，不然它在瀑布里的位置就乱了 |
| 怎么验没搬丢东西 | 改之前和改之后两轮日志，按断言标签逐条比对 | 1221 条断言一条没少，差异只有 7 条改了措辞的日志；依赖宽度和位置的断言数值也都没变 |

这套版面本身也是在用运行时：外层是 `UIScrollView` 套 `UIStackView`，上下留白和标题的缩进用的是内边距，没有多套一层视图。

## 它同时是示例和测试套件，这两个角色要分开

定交付物时看清楚的一件事：`acceptance/` 今天装着一千七百多条断言，而对外要交付的是一个**干净的 hello world**。一个目录当不了两个角色——示例交不出去，验收也没法独立演进。

所以改名叫 `acceptance/`（它真正是什么），示例另起 `examples/hello/`。两个都是「一个 Nacre 项目」，形状一样。
